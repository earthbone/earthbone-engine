# Test log

Phase 2 of `TEST_PLAN.md`. One entry per commit: what was added, what it
found, and what it still cannot catch. The last part is the one worth reading,
since a technique that catches nothing today is still buying coverage against
a change nobody has made yet, and a technique that catches nothing ever should
be removed.

Tiers, as the plan set them. Tier 1 runs on every commit and stays under five
minutes. Tier 2 is nightly. Tier 3 is weekly.

## 1. `esm`, property based load order

Tier 1. `crates/esm/tests/prop_load_order.rs`, with the shared seed and
reproduction helper in `crates/esm/tests/common/mod.rs`.

**Added.** Four properties over generated load orders of one master and one to
four patches, each patch writing, deleting or ignoring each shared object, some
of them light, some defining records of their own:

- the last file to write a form is the winner, its editor id and deletion flag
  are the ones that file wrote, and the override list holds every writer
- a plugin serialised, parsed and serialised again gives the same bytes, and
  every case builds its order from the reparsed plugin so the parser sees
  generated bytes rather than a model handed straight to it
- a runtime FormID is the file's slot over the object, twelve bits behind
  `0xFE` for a light file and a whole byte for a regular one, and a file's own
  record resolves back to that file
- the cell index holds exactly the references the plan placed, with a deleted
  winner moving to the deleted list rather than vanishing

The oracle for the last one is the plan the generator followed, not a second
scan of the same records. A re-scan would re-implement `CellIndex` and agree
with it for the same wrong reason.

**What it found.** No defect in the engine. Two checks on the tests themselves
were worth their time. Raising `PROPTEST_CASES` from 192 to 20,000 raised the
runtime from 0.02 s to 1.88 s, which is the hundredfold that proves the cases
are really sampled rather than silently skipped. Breaking the winner oracle on
purpose, so it expected the master to win every time, failed on the first case
and shrank to one object and one patch, which proves the property bites. The
regression file records that deliberate break and nothing else, and says so.

**A tiering problem this commit exposed, unrelated to its own cost.** The four
properties add 0.02 s at the committed 192 cases. But the gate's own
`cargo test --workspace` in a debug profile takes 692 s, which is more than
twice the five minute tier 1 budget the plan set, and that is before anything
in phase 2 lands. The cost is not here, it is the gated runs against the
installed game and the 60 save corpus. Tier 1 needs to mean the default run
with `SKYRIM_DATA` unset, and the gated runs need to move to tier 2, otherwise
the budget is already broken and every later commit gets blamed for it.

**What it cannot catch.** Everything the generator does not vary: compressed
records, `XXXX` extended lengths, more than one master per patch, exterior
cells and worldspace grids, more than five objects or four patches, and the
64-bit edges of the ESL slot space. It says nothing about parsing files it did
not itself emit, which is what the fuzz targets and the vanilla live runs are
for, and nothing about what any of the records mean.

## 2. `papyrus`, structure aware VM and assembler fuzzing

Tier 2, nightly. `fuzz/fuzz_targets/fuzz_vm_run.rs` and
`fuzz/fuzz_targets/fuzz_pex_grammar.rs`, with `arbitrary` added to the fuzz
workspace. Regression tests in `crates/papyrus/tests/asm_arity.rs` and
`crates/papyrus/tests/vm_limits.rs`, both tier 1 and both instant.

**Deviation from the plan, on purpose.** The plan said to switch `fuzz-pex` to
a grammar. It is added beside it instead. The byte target reaches the parser's
error paths and has already found five crashes there, and a grammar target
almost never produces an invalid file, so switching would have traded working
coverage for new coverage rather than gaining it.

**Added.** `fuzz-vm-run` picks opcodes and operands with `arbitrary`, assembles
real PEX through `ScriptBuilder`, loads it and runs it under two budgets, so
the interpreter is fuzzed rather than only the loader. `fuzz-pex-grammar`
builds a script from a grammar, writes it, parses it back and writes it again,
and asserts the two serialisations match, which catches a reader or writer
losing a field without anything panicking.

**What it found.** Three defects in twenty minutes of fuzzing, two fixed here.

1. **`asm::write` panicked on an instruction with too few operands.** Found in
   under five minutes, smallest possible case: one `CallStatic`, no operands.
   The writer sliced `args[..3]` on an empty list and died with "range end
   index 3 out of range for slice of length 0", a message naming neither the
   opcode nor the function. The writer returns `Vec<u8>` and has no error
   channel, so it now pads the fixed operands with `Operand::None`, which is a
   real operand in this format. Regression test covers every opcode given no
   operands at all.
2. **`ArrayCreate` allocated whatever a script asked for.** One instruction
   asked for 26.5 GB. The negative case was already refused, the large positive
   one was not. Now capped at `MAX_ARRAY_LEN`, a million elements. This is not
   an invented hazard: the Creation Kit wiki warns authors about it directly
   for `Utility.CreateArray`, saying size is treated as unsigned and negative
   numbers "can cause major issues". Vanilla asks the author to be careful,
   this refuses instead. The same run then found **`StrCat` growing without
   bound**: `StrCat dest, dest, dest` doubles its input, so a loop passes a
   gigabyte in about thirty passes and the step budget never binds. Capped at
   `MAX_STRING_LEN`. After both caps the VM target ran ten minutes clean.
3. **The assembler kept operands the writer discards.** A non-variadic opcode
   given extra operands interned their strings into the string table but never
   wrote them into the code, so a round trip dropped the unused entry and the
   two serialisations differed. `FunctionBuilder::ins` now truncates to the
   opcode's arity when there is no variadic tail.

**Still open, not fixed.** After that third fix `fuzz-pex-grammar` still finds
a disagreement, and it is a different one: the instruction count field is
written as 2 and read back as 1, so the reader is dropping an instruction from
a stream the assembler is willing to emit. Reproduce with
`cargo +nightly fuzz run --fuzz-dir fuzz fuzz-pex-grammar` and the artifact it
writes. It is left open rather than guessed at, because the fix belongs with
whoever can say which side is wrong: the reader for stopping early, or the
assembler for emitting a stream that is not representable. Until then the
nightly tier fails on this target, which is the correct state for a known
defect.

**What this entry cannot catch.** `fuzz-vm-run` builds one function on one script with
no properties, no states and no object graph, so it never reaches inheritance,
property dispatch, latent calls or the scheduler, which is where the
interesting VM state lives. Neither target models natives, so everything
behind `CallStatic` and `CallMethod` is a stub to them. The budgets that stop a
hang also stop a slow leak from ever showing. Neither target says anything
about whether a script computes the right answer, only that it does not take
the process down.

## 3. `save`, the vanilla loader on bytes nobody wrote

Tier 2, nightly. `fuzz/fuzz_targets/fuzz_save.rs`.

**Added.** A fuzz target over `Save::parse`, asserting two things: parsing any
byte string does not panic, and a save that parses writes back to exactly the
bytes it came from. The second half matters more than the first. The reader
already round trips all sixty real saves byte for byte, but those are files the
game itself wrote. A save in the wild comes from a crash, an older build, a
different mod list or a hand edit, and a reader that silently drops a field
would look correct right up until someone saves over their game with a
shortened file.

**What it found.** Nothing. 99,273,231 executions in 361 seconds, 445 edges
covered, no crash and no round trip difference. That is a real result rather
than an absence of one: the loader was written against the UESP pages and
ReSaver over two days, and it holds up against a hundred million hostile
inputs.

**What it cannot catch.** It only reaches what `Save::parse` parses. The
Papyrus tail past the reference table is still handed back raw, so nothing here
exercises it. It says nothing about whether a parsed save means the right
thing, which is what the quest stage progression test over the 41 save sequence
covers, and nothing about the engine's own `SOEV`, `SOEW` and `SOEG` streams,
which live in crates a different fork owns.

## 6. `papyrus`, the open grammar defect, decided

Tier 1, plus one tier 2 corpus check. `crates/papyrus/tests/asm_unique_names.rs`
and `crates/papyrus/tests/real_unique_names.rs`.

**The defect, precisely.** Phase 2 recorded it as an instruction count written
as 2 and read back as 1. That was the right symptom read from the wrong field:
it is the **debug function count**, a `u16` in the debug block, not the
instruction count in a function body. The minimal case is two functions given
the same name in one state, each carrying line numbers.

**Which side was wrong: the assembler.** `ScriptBuilder::function_in` appended,
so a caller could build two functions named `Go` in one state. The reader then
attaches each debug entry to a function by name with `find`, which returns the
first, so both entries landed on the first function and the second came back
with no lines at all. Rewriting emitted one debug entry where the first wrote
two, and the round trip differed.

The reader is right and the file it was handed was not representable:

- Papyrus has no overloading and a state defines each function once.
- Caprica rejects it at compile time, `PapyrusObject.cpp:167`, "a function
  named X was already defined in this object".
- Every compiled script Bethesda ships agrees. 14,026 scripts parsed, 15,635
  states, 54,620 functions, **zero** states defining a function twice.

That last check is the one that could have overturned the fix rather than
confirmed it, which is why it is a test and not a paragraph. If a counter
example ever ships, it fails and the decision gets revisited.

**The fix.** `function_in` replaces a same named function instead of appending,
which keeps the builder total with no error channel to add, and matches what
`FunctionBuilder::ins` already does when it drops operands the writer would not
emit. `fuzz-pex-grammar` passes, so the nightly tier is green again.

**What it cannot catch.** Only functions are deduplicated. Two properties of
one name, two variables of one name, or two states of one name are still
buildable and would break the same way through a different path, since the
reader matches those by name too. Nothing here checks a name against the parent
object's names, which is the other half of what Caprica enforces.

## 7. `bsa`, fault injection on the read path

Tier 1, in `crates/bsa/src/archive.rs`'s test module because the synthetic
archive builders are `pub(crate)`.

**Deviation from the plan, and why.** The plan says failpoints with the `fail`
crate. There is nowhere useful to put one. The only IO on this path is a single
`std::fs::read` in `Archive::open`, and everything after it works on a `Vec<u8>`
already in memory, so there is no partial read to interrupt and no slow disk to
simulate. Corrupting the bytes reaches the same code deterministically, without
adding a dependency or a global failpoint registry, which also suits the
project's rule about dependency scope. No `fail` dependency was added. The save
write path, the other half the plan pairs this with, is in `crates/game` which
another fork holds, so it is still not done.

**One real defect, and it was the silent kind.** An archive states how long a
file is once unpacked, and the index peeks that value. Neither decompressor
checked it: `expected_size` was passed in and used only to size the output
buffer. So a record declaring 4,119 bytes whose stream held 23 returned 23
bytes and `Ok`. Every caller, the mesh reader, the texture decoder, the script
loader, would then work on a truncated buffer believing it complete. Minimal
case in `a_decompressed_file_shorter_than_declared_is_refused`: build the
one-file compressed archive, overwrite the four declared-size bytes at the
record's offset, leave the stream untouched.

Fixed with `check_size`, a new `Error::DecompressedSize`, and the rule that a
declared length of zero is not checked, since an off-disk index leaves it zero
by design and an empty file is not a mismatch. Verified not to be too strict
against every shipped archive: **172,961 files across all of them still read**,
which is the test that would have caught an overzealous rule.

**Two sweeps, both already clean.** Every prefix of a valid archive, and one
flipped bit at every position and every bit of the header and tables. Both
index-or-refuse and read-or-refuse without a panic. They found nothing, which
is worth keeping anyway: they cost 0.24 s and they are the tests that fail when
someone adds an unchecked slice.

**What it cannot catch.** Nothing here exercises BA2, only BSA v104 and v105.
Nothing covers a `dds_info` rebuild path corruption. The bit-flip sweep stops
at the first 96 bytes, so the payload itself is only covered by truncation. And
a declared size that is wrong but self-consistent, a stream that really does
decompress to the lie, is indistinguishable from a healthy file by design.

## 8. `dds` and `bsa`, structure aware fuzz targets

Tier 2, nightly. `fuzz/fuzz_targets/fuzz_dds_grammar.rs` and
`fuzz/fuzz_targets/fuzz_bsa_grammar.rs`.

**The gap both fill is the same one.** `fuzz-dds` calls `Dds::parse` and stops,
and `fuzz-bsa` calls `index_archive_in` and stops. Random bytes almost never
form a header or a table either one accepts, so in both crates the code behind a
successful parse, the decoder and the record read path, had never been fuzzed at
all. That is where the arithmetic lives: block counts, mip chains and surface
sizes in one, offsets, packed sizes and declared lengths in the other.

Each target builds a well formed container around fuzzer chosen fields, then
runs the stage the byte target never reaches. The DDS one decodes every mip of
every layer and asserts a decoded image is whole RGBA pixels and that the pixel
count matches the dimensions reported beside it. The archive one indexes, reads
every record, and asserts that a record declaring an unpacked length hands back
exactly that many bytes, which is the invariant entry 7 found broken.

**Runs, five minutes each, all clean.**

| Target | Runs | Time |
|---|---|---|
| `fuzz-dds-grammar` | 19,979,275 | 301 s |
| `fuzz-bsa-grammar` | 1,634,668 | 301 s |
| `fuzz-pex-grammar` | 2,378,411 | 301 s |

The third is the one entry 6 fixed. It fails on the old assembler and passes
now, so the nightly tier is green across every target again.

**How to run these here**, since phase 2 recorded that it could not. `cargo
fuzz` needs a nightly `rustc`, and this machine has Homebrew's stable `rustc`
first on `PATH`, so `rustup run nightly` and `RUSTUP_TOOLCHAIN` both fail:
cargo-fuzz shells out to a `cargo` that resolves back to the Homebrew stable
one. Putting the rustup shims first is what works:

```text
env -C <repo> PATH=$HOME/.cargo/bin:/usr/bin:/bin RUSTUP_TOOLCHAIN=nightly \
  cargo fuzz run fuzz-dds-grammar -- -max_total_time=300
```

**No mesh grammar target, and the reason.** A valid `NIF` is a block graph with
a string table and version-dependent layouts, so a grammar that produces one is
a large piece of work rather than a session's. A shallow version would mostly
generate files the parser rejects, which is what `fuzz-nif` already covers with
plain bytes. Left undone deliberately rather than done badly. The mesh reader
did get a real defect fixed today by other means, the partition-local bone
indices, found by rendering rather than by fuzzing.

**What these cannot catch.** The DDS target never builds a legal payload on
purpose, so it exercises truncation and bad geometry far more than correct
decoding, and it asserts self consistency rather than correct pixels. The
archive target only builds BSA with one folder, never BA2 and never the DX10
texture rebuild path. Neither says anything about whether a file that decodes
cleanly decodes *correctly*, which only the corpus tests against real data do.
